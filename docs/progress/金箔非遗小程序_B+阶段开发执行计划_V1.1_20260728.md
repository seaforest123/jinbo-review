# 金箔非遗小程序 B+ 阶段开发执行计划

> 文档版本：V1.1 正式合并版\
> 制定日期：2026-07-28\
> 适用项目：金箔非遗数字体验与活化传播微信小程序\
> 当前决策：近期主线继续采用原生微信小程序 B+ 路线；方案 A 暂不进入正式开发，仅保留为后续独立技术验证方向。\
> 替代关系：本文件替代 V1.0，已合并《V1.1 补充条目》中的有效建议，并按当前工程约束完成修正。

## 1. 文档用途

本计划用于指导当前小程序从“功能可运行”推进到“普通用户能顺利完成、操作流畅自然、五步体验各有趣味、内容可正式展示”的阶段。

后续新增需求、安排开发工作和验收版本时，应优先参照本计划。若需求明显超出本计划范围，应先评估工期、资源体积、兼容性和对现有流程的影响，再决定是否进入当前版本。

## 2. 核心结论

近期不迁移 Cocos Creator，不把项目改造成微信小游戏。

当前项目已经是可运行的原生微信小程序，五道工序、共享金箔状态、入门辅助、完成上限、错误拦截和主要界面已经具备。下一阶段最有价值的工作不是更换技术框架，而是补齐以下四类体验：

1. 先释放离线资源预算，为声音、真实媒体和后续代码增长留出安全空间；
2. 补充声音、触觉、动效和危险提示，让操作更有反馈；
3. 区分五道工序的输入方式与视觉表现，解决“每一步都像在重复同一种操作”的问题；
4. 接入真实照片、短视频，并通过真机和新手测试保证展示质量。

推荐目标排期为 4～5 周；若素材、测试者或设备准备延迟，应按 5～6 周安排。只有在素材已齐、测试者已提前约定，并暂缓 P1 的主动定位检查玩法时，才适合尝试压缩到约 3 周。

## 3. V1.1 合并说明

本版正式吸收以下补充建议：

- 将资源预算腾挪设为反馈系统开发前的前置任务；
- 为五道工序定义不同的操作原语；
- 区分打箔、检查、出箔三个环节的材质和状态表现；
- 增加 90 秒以内的评委演示模式；
- 将 10 人新手测试拆成两轮，提前发现流程问题；
- 将排期从理想化 3～4 周修正为目标 4～5 周、风险情形 5～6 周。

同时修正以下不可直接实施或存在冲突的表述：

- 音效不要求全部进入主包。高频、低延迟关键音效本地化，低频环境音和非关键提示可预加载、缓存或远程加载；
- 项目当前的 2 MiB 是自定义离线包发布警戒线，不直接等同于平台统计口径下的“微信主包大小”；
- 手机触控不可靠提供真实压力值，“力度”统一使用按压时长、手势幅度、移动速度等可测数据推断；
- 裁剪采用“匀速滑动控制”，不使用无法稳定采集的“匀速力度”；
- 检查仍只完成并锁定一次，但一次检查流程内部最多允许 3 个定位探针，不与现有状态上限冲突；
- 高频连续震动改为稀疏的节点震动，避免设备差异、噪声和用户不适；
- 现有资源审计禁止远程媒体，资源迁移时必须同步升级审计规则，不能只替换素材路径。

## 4. 当前项目基线

### 4.1 已具备的能力

- 原生微信小程序工程可编译运行；
- 五道制作工序使用同一份金箔状态，前一步操作会影响后一步；
- 裁金片和装箔均限制为最多 3 片，达到上限后锁定；
- 裁剪不符合要求时不会直接判定合格，入门辅助仅在接近目标时生效；
- 锤击完成后默认锁定；从检查环节明确返回时，只允许一次返工；
- 检查完成后锁定，避免无限扫描；
- 最终抛光达到 100% 后锁定，并防止重复提交；
- 新手辅助可以保证用户在提示下完成完整五步流程；
- 首页、体验页、主要标题和按钮已完成一轮居中、字号与层级优化；
- 已具备金箔厚度、覆盖、风险、瑕疵和完成质量的可视反馈；
- 已有短视频和帧动画的本地候选素材接入结构；
- 自动化测试当前为 203 项全部通过。

### 4.2 当前技术与资源状态

- 工程类型：微信小程序，不是微信小游戏；
- 项目当前离线包审计结果：2,000,887 字节；
- 当前离线动画素材：344,388 字节；
- 当前离线视频素材：284,362 字节；
- 当前本地素材总数：25 个；
- 按项目自定义 2 MiB 发布警戒线计算，只剩约 96,265 字节余量。

当前审计脚本统计整个 `miniprogram` 目录，并明确禁止远程媒体。因此，“迁云”不是单纯替换地址，还需要同步完成媒体域名白名单、加载失败降级、缓存策略及审计规则调整。

后续真实照片、视频和大体积音频原则上不得继续大量放入离线包。离线包仅保留启动必需图片、关键低延迟音效、低体积动效和断网兜底素材。

## 5. 本阶段目标与非目标

### 5.1 阶段目标

完成本计划后，小程序应达到以下状态：

- 第一次使用的业余用户能看懂每一步要做什么；
- 用户操作错误时能及时知道“错在哪里、如何修正”；
- 每道工序达到数量或进度上限后立即锁定，不再继续累加；
- 五道工序具有可区分的操作方式，不再只是同一种点击或拖动的换皮；
- 五道工序都有可感知的声音、视觉或触觉反馈；
- 页面切换、拖动、点击、扫描、敲击和完成反馈自然连贯；
- 打箔、检查、出箔使用同一状态数据，但呈现不同的视觉材质和任务目标；
- 真实照片和视频接入后不明显拖慢首屏和核心操作；
- 评委或访客能在 90 秒内体验核心闭环并看到成品；
- 真机连续完成三次流程，不出现卡死、状态错乱或无法进入下一步；
- 形成可用于汇报和后续迭代的截图、录屏、测试记录及问题清单。

### 5.2 本阶段不做

- 不迁移 Cocos Creator；
- 不改造成微信小游戏；
- 不在当前版本建设完整 3D 场景或复杂物理引擎；
- 不为追求“游戏级效果”重写现有五步业务逻辑；
- 不一次性加入大量未经筛选、未经压缩的照片和视频；
- 不依赖真实压力传感或机型不稳定的触控能力；
- 不在专业内容尚未确认前，把候选说明写成确定性非遗事实；
- 不扩展与流程完成率、展示效果或真机稳定性无直接关系的大型模块。

## 6. 总体优先级

| 优先级 | 工作项 | 原因 |
| --- | --- | --- |
| P0 | 新手可完成性、状态上限、错误提示、崩溃与卡死 | 决定用户能否使用 |
| P0 | 离线资源预算腾挪和审计规则升级 | 决定音效与真实媒体能否安全接入 |
| P0 | 音频管理、锤击危险反馈、关键触觉反馈 | 直接改善趣味性和操作确认感 |
| P0 | 真机兼容与性能测试 | 开发者工具流畅不等于真实手机流畅 |
| P1 | 五道工序操作原语与视觉表现差异化 | 解决五步体验单调和重复的问题 |
| P1 | 真实照片、短视频和统一视觉素材接入 | 提升真实性、展览感和汇报质量 |

## 7. 分阶段执行计划

### 阶段 0：冻结可运行基线

预计工期：0.5～1 个工作日。

#### 工作内容

- 保存当前可运行版本的测试结果和资源审计结果；
- 建立一份五步标准操作路径；
- 在至少一台真实手机上录制当前版本完整流程；
- 记录当前已知问题，不在后续修改中丢失已有正确行为；
- 将“203 项测试全部通过”和“资源审计通过”作为回归基线。

#### 验收标准

- `npm test` 全部通过；
- `npm run audit:assets` 通过；
- 五步流程可以完成；
- 当前版本录屏、关键页面截图和问题清单可查阅。

### 阶段 0.5：离线包瘦身与资源准入

预计工期：1～2 个工作日。此阶段是统一音频接入的前置任务。

#### 7.0.1 资源盘点

- 复核离线动画、视频、图片及其他资源的真实引用关系；
- 标记“启动必需”“高频即时反馈”“可延迟加载”“仅展示”“可删除”五类资源；
- 删除只允许在确认无引用、已有备份且回归测试通过后进行；
- 统计迁移前后离线包、动画、视频和图片的体积变化。

#### 7.0.2 迁移策略

- 候选视频优先迁移到项目可控的云存储或稳定 HTTPS CDN；
- 大体积帧动画优先改为远程帧、CSS/Canvas 轻量表现或按需加载；
- 主包保留每类媒体的低体积占位图和核心流程降级表现；
- 需要即时响应的短音效可本地保留；
- 低频环境音、旁白和非关键音效可采用预加载或缓存；
- 若使用微信分包，应同时记录“主包体积”和“全部离线包体积”，避免混用指标。

#### 7.0.3 审计规则升级

现有审计规则禁止任何远程媒体。迁移时必须同步：

- 只允许配置表中明确登记的 HTTPS 媒体域名；
- 拒绝 HTTP、临时分享链接和未登记域名；
- 校验每个远程资源都有本地海报、占位或无媒体降级方案；
- 继续限制本地单文件、动画合计、视频合计和全部离线包体积；
- 为关键音效建立独立体积预算；
- 测试资源加载失败时核心五步仍可完成。

#### 7.0.4 资源准入规则

任何新增资源进入离线包前，必须回答：

1. 是否影响首屏或高频交互？
2. 是否必须在无网状态播放？
3. 是否可转为远程资源并预加载？
4. 是否已有同类资源可以复用？
5. 压缩后体积是多少？
6. 是否具有来源和使用授权？

#### 阶段 0.5 验收标准

- 项目自定义 2 MiB 警戒线下的可用余量不低于 400 KiB；
- 为关键本地音效预留 80～160 KiB 的独立预算；
- 迁移后弱网与断网场景下五步核心流程仍可完成；
- 远程媒体失败时显示占位或轻量降级，不出现空白死区；
- 审计脚本和自动化测试已适配新的本地/远程混合资源策略；
- 资源准入规则已写入项目文档。

400 KiB 是项目阶段目标，不是微信平台固定要求。若评估后无法达到，应减少本地媒体数量，不得通过直接放宽审计警戒线掩盖问题。

### 阶段 1：反馈系统与操作差异化

预计工期：7～10 个工作日。

#### 7.1 统一音频管理

建立统一的音频管理模块，不允许各页面重复创建、无序播放音频实例。

第一版不追求 20～25 个音效全部落地，先接入 8～12 个辨识度最高的关键音效：

- 通用：轻触、确认、步骤完成、最终完成；
- 裁金片：合格或裁偏；
- 装箔：放置和达到 3 张；
- 打箔：标准击和危险预警；
- 检查：扫描或发现瑕疵；
- 出箔：抛光和完成。

第二批再补充环境音、节奏层和细分状态音，避免第一版因资源量过大阻塞开发。

实现要求：

- 遵守微信端首次用户操作后才能稳定播放声音的实际限制；
- 高频关键音效本地化，确保按下后及时反馈；
- 远程或低频音效在进入对应页面前预加载，失败时静默降级；
- 页面退出、隐藏或重进时停止或恢复正确的音频；
- 音频加载失败不得阻断五步流程；
- 同类高频音效限制并发，避免锤击时声音叠成噪声；
- 提供总开关，并记住用户的静音选择；
- 背景音、环境音和操作音分开控制音量；
- 音频实例在页面退出或应用隐藏时正确释放。

#### 7.2 触觉与视觉反馈

- 关键成功操作使用轻触觉反馈；
- 达到上限、危险敲击和最终完成使用不同节奏或视觉替代；
- 不支持触觉的设备自动降级，不弹错误提示；
- 不使用持续高频震动模拟“阻力”，只在越界、吸附、命中和完成节点震动；
- 动效优先使用 `transform` 和 `opacity`，减少高频布局重排；
- 所有动画不得遮挡操作目标或阻止用户继续；
- 低性能设备允许减少粒子、阴影和同时播放的动画数量。

#### 7.3 五道工序操作原语与趣味性

操作差异化不得改变现有共享状态、完成上限和入门辅助的正确逻辑。

##### 工序 1：裁金片

- 操作原语：匀速滑动控制；
- 用户按住裁刀沿目标轴向推进；
- 判定由位置误差扩展为“位置误差 + 速度稳定性”；
- 速度突变时显示裁口不齐的视觉反馈和方向性提示；
- 接近目标才触发吸附；
- 入门模式放宽稳定性阈值，不因短暂抖动反复失败；
- 合格 3 片后出现“已备齐”反馈并锁定操作。

区分点：唯一以滑动速度稳定性为主要技巧的工序。

##### 工序 2：装箔

- 操作原语：快速移动、进入目标区后减速并短暂停留；
- 金片移动过快时出现轻微形变或飘动提示；
- 抵达目标区后需减速停留，再确认放置；
- 快速松手时判为偏移，但不能造成不可恢复的死局；
- 减速进入目标区时提供渐强吸附高亮和提示音；
- 入门模式保留近目标吸附，并放宽停留阈值；
- 第 3 张放入时给出明显完成反馈并锁定。

区分点：唯一包含“减速进入 + 停留确认”的工序。

##### 工序 3：打箔

- 操作原语：节奏、落点、推断力度三维输入；
- 推断力度来自按压时长、触点移动幅度或手势速度，不依赖真实压力传感；
- 危险区域必须在破损前明确预警，不能只在失败后告知；
- 使用颜色、轻微抖动、裂纹征兆和音效表达风险；
- 装箔对齐更好的区域，在专业模式下拥有稍大的有效落点容错；
- 装箔偏移较大的区域，在专业模式下容错适度收窄；
- 入门模式显著减弱前序状态对容错的影响，优先保证完成率；
- 完成一轮后锁定；只有从检查页明确选择返工，才开放一次敲击。

区分点：唯一的节奏、多落点和力度推断复合输入工序。

##### 工序 4：检查

- 操作原语：主动定位探索；
- 一次检查流程中最多使用 3 个定位探针；
- 用户依据光带、亮度、声音或方向提示逐步定位瑕疵；
- 3 个探针结束、找到主要瑕疵或入门辅助直接确认后，完成此次检查并锁定；
- 检查在业务状态上仍只完成一次，不允许完成后反复扫描；
- 入门模式直接提示大致方位，并保证不会因定位失败无法继续；
- 返回返工时保留原有金箔状态，不重新开始。

区分点：唯一以获取信息而非直接改变金箔状态为目标的工序。

此项为 P1。若阶段 1 超期，可先保留现有单次扫描交互，将三探针探索延后，但不得影响其余 P0 验收。

##### 工序 5：出箔

- 操作原语：连续抚平、覆盖表面、稳定收尾；
- 抛光由离散点击改为连续拖拽；
- 25%、50%、75%、100% 设置清晰阶段反馈；
- 达到 100% 后进入约 0.5 秒的稳定收尾；
- 收尾失败不重置抛光进度，只提示再次稳定停留；
- 表面光泽和平整度随拖拽覆盖实时变化；
- 100% 完成后锁定并防止重复提交；
- 完成时展示前后对比、质量摘要和五步操作痕迹。

区分点：唯一包含连续覆盖和稳定保持的工序。

#### 7.4 三种材质状态渲染

打箔、检查、出箔继续读取同一份金箔状态，但不得复用完全相同的网格外观：

- 打箔：侧重锤击痕迹、厚薄变化、落点和破损征兆；
- 检查：侧重扫描光带、瑕疵标记、方向线索和定位结果；
- 出箔：侧重表面平整度、光泽、柔和高光和成品质感。

三屏应共享“状态值 → 视觉参数”的纯映射逻辑，避免同一数据在不同页面产生矛盾结论；渲染组件或样式可以不同。

格内原始数值只在开发调试模式显示。正式版本使用汇总指标、颜色、纹理和状态文案表达，不让普通用户直接阅读大量技术数字。

#### 阶段 1 验收标准

- 五道工序每一步至少有一种声音反馈和一种视觉反馈；
- 关键完成与危险状态有可区分的触觉或替代视觉反馈；
- 静音、页面切换、后台恢复和音频加载失败均不会阻断流程；
- 达到 3 片、完成检查或 100% 等上限后不能继续累加；
- 五道工序的主要输入方式具有明显差异；
- 体验者在完成一次流程后，至少 8/10 能正确描述五步操作方式的主要差别；
- 专业模式能感知装箔状态对打箔容错的轻微影响；
- 入门模式下该关联不明显降低完成率；
- 打箔、检查、出箔三屏的状态表现可以一眼区分；
- 新手模式连续完成三次，不需要开发人员代操作；
- 自动化测试和资源审计继续通过。

### 阶段 2：真实媒体、视觉统一与演示模式

预计工期：5～8 个工作日；真实媒体部分从收到可用素材后开始计算。

#### 7.5 素材接收方式

用户可以先提供照片或视频链接用于筛选和确认，但正式接入前应满足以下任一方式：

1. 提供可长期访问的稳定 HTTPS 直链；
2. 提供原始文件，由项目统一压缩并上传到云存储或 CDN；
3. 提供网盘或临时下载链接，下载后转存到项目可控的存储位置。

不建议正式版本长期依赖聊天附件、临时分享链接、需要登录的网页地址或随时可能失效的第三方链接。

每份素材至少记录：

- 文件名或素材编号；
- 展示内容；
- 拍摄者或来源；
- 是否获得展示授权；
- 拍摄时间和地点（若适用）；
- 对应页面或工序；
- 是否允许裁剪、压缩和加字幕；
- 专业说明是否已经确认。

#### 7.6 图片与视频处理原则

图片：

- 原图保留在素材归档区；
- 小程序使用压缩后的 WebP、JPEG 或适合场景的 PNG；
- 首页首屏图、步骤图和缩略图使用不同尺寸；
- 加载失败时显示本地占位图；
- 非首屏图片使用懒加载。

视频：

- 优先使用短视频和明确的封面图；
- 编码、分辨率和码率以真机兼容与清晰度平衡为准；
- 视频默认不自动带声音播放，避免与背景音冲突；
- 首屏不预加载大视频；
- 网络较差时允许只显示封面和文字说明；
- 视频上传到项目可控的云存储或稳定 CDN。

#### 7.7 视觉统一

- 统一标题、正文、说明、数据、按钮和状态标签的字号层级；
- 统一金色、墨色、米白和危险色的用途；
- 真实照片与数字交互区使用一致的圆角、边框和留白；
- 避免每个步骤使用完全不同的装饰风格；
- 统一设计语言，但不抹平五道工序在材质和交互上的差异；
- 优先提升信息层级和可读性，不以增加装饰数量作为美化标准；
- 所有主要页面适配系统胶囊区域、窄屏和常见全面屏。

#### 7.8 评委演示模式

预计工期：0.5～1.5 个工作日，优先级 P1。

进入方式：

- 优先使用带 `mode=demo` 参数的专用体验二维码；
- 内部体验环境可显示“90 秒演示”入口；
- 正式用户首页不默认突出该入口，避免与正常五步流程混淆。

演示路径：

- 预置裁金片和装箔后的合法状态；
- 直接进入“打箔 → 检查 → 出箔”核心闭环；
- 默认开启入门辅助；
- 在 90 秒内完成并看到成品结果；
- 使用与正常流程完全相同的状态结构、控制器和判定逻辑；
- 仅通过初始化参数和预置状态进入，不复制三套独立业务代码。

数据隔离：

- 演示状态不得覆盖用户正常进度；
- 演示完成记录不得混入正常完成率统计；
- 若当前埋点协议暂不支持 `demo` 模式，则演示模式先关闭行为上报，不得临时写入不符合闭合数据结构的字段；
- 退出演示后重新进入正常流程，必须得到正常初始化状态。

#### 阶段 2 验收标准

- 所有正式素材均有来源和授权状态记录；
- 真实媒体使用稳定地址，临时链接不进入发布配置；
- 弱网或媒体加载失败时仍可完成五步流程；
- 首页首屏不因加载视频而长时间空白；
- 五步页面的字体、按钮、状态颜色和间距保持一致；
- 新增素材后资源审计仍通过；
- 无项目背景的体验者可在演示模式下 90 秒内完成三步核心闭环；
- 演示模式和正常流程状态互不污染；
- 演示模式没有复制独立的业务状态机。

### 阶段 3：真机测试、可用性修正与交付

预计工期：4～6 个工作日。测试者招募和时间协调应在阶段 1 开始时同步进行。

#### 7.9 测试设备

至少覆盖：

- 一台中低性能 Android 手机；
- 一台主流 Android 手机；
- 一台近年 iPhone；
- 微信开发者工具只用于辅助定位，不代替真机验收。

#### 7.10 必测场景

- 首次进入、再次进入和从后台恢复；
- 开启声音、静音和系统媒体音量较低；
- 正常网络、弱网、远程媒体加载失败和短暂断网；
- 快速连续点击、重复手势、误触和中途退出；
- 五步正常完成、工序返工、查看提示和重试；
- 裁剪 3 片、装箔 3 张、敲击完成、检查完成、抛光 100% 后继续操作；
- 页面切换时音频、动画、定时器和状态是否正确释放；
- 不同屏幕宽度、系统字体设置和胶囊位置；
- 演示模式进入、退出、重复进入和切换正常模式；
- 连续完成三轮，观察内存、发热、卡顿和状态污染。

#### 7.11 两轮新手可用性测试

建议邀请 10 名没有项目背景、没有金箔制作经验的体验者。

第一轮：

- 阶段 1 结束后进行；
- 4～5 人；
- 可使用占位媒体；
- 目标是尽早发现流程阻塞、手势不清和提示无效；
- 发现的 P0 问题在阶段 2 期间同步修复。

第二轮：

- 阶段 2 基本完成后进行；
- 补足累计 10 人；
- 使用接近交付状态的真实媒体和演示模式；
- 用于最终完成率和发布验收。

每位体验者记录：

- 是否能在不看开发说明的情况下开始；
- 卡住的步骤和停留时间；
- 请求提示的次数；
- 误操作次数；
- 是否需要旁人代操作；
- 是否成功完成五步；
- 是否能区分五步的操作方式；
- 是否能在演示模式下 90 秒内完成核心闭环；
- 对趣味性、真实感、清晰度和流畅度的主观评价。

阶段通过标准：

- 累计至少 8/10 名新手可在不由开发人员代操作的情况下完成；
- 没有人因为状态上限、按钮失效或流程死锁而无法继续；
- 连续三轮完整流程无崩溃、无数据串轮、无重复提交；
- 不存在阻断发布的 P0 问题和高频 P1 问题；
- 中低性能设备没有连续 300 毫秒以上、明显影响操作的卡顿；
- 媒体加载失败时核心制作流程仍可使用；
- 第一轮与第二轮问题、修复和复测结果均有记录。

#### 7.12 交付物

- 可运行的小程序版本；
- 自动化测试报告；
- 资源审计结果；
- 真机测试设备与问题记录；
- 两轮共 10 名新手体验结果摘要；
- 首页和五道工序的成套截图；
- 一段从首页进入到完成结果的完整录屏；
- 一段 30～60 秒的精简演示视频；
- 一个可进入 90 秒演示模式的体验入口；
- 已知限制与下一版建议；
- 素材来源、授权与存储位置清单；
- 离线包资源准入规则。

若第一轮测试出现流程死锁或大量用户无法理解手势，应暂停视觉扩展，优先修复可完成性，不得把问题全部积压到最后一周。

## 9. 每次迭代的完成定义

一项功能只有同时满足以下条件，才标记为“完成”：

- 功能行为与本计划一致；
- 正常路径、错误路径和重复操作都已验证；
- 新手模式能继续完成流程；
- 不破坏数量上限和状态锁定；
- 页面退出或重进后状态符合设计；
- 低性能设备有合理降级；
- 新增代码具有必要测试；
- 全量自动化测试通过；
- 资源审计通过；
- 关键界面已真机截图或录屏确认；
- 文案涉及专业事实时，已确认来源或标记为候选内容。

仅在开发者工具中“看起来能用”，不视为完成。

## 10. 风险与应对

| 风险 | 可能影响 | 应对方式 |
| --- | --- | --- |
| 离线包余量仅约 94 KiB（约 96 KB） | 新音频、照片和视频导致审计失败 | 阶段 0.5 先迁出非关键动画和视频，目标余量至少 400 KiB |
| 审计规则当前禁止远程媒体 | 迁云后自动化测试失败或放松安全边界 | 改为 HTTPS 域名允许列表，并强制占位和失败降级 |
| 音效数量一次扩展过多 | 包体、制作和调试周期失控 | 第一批只做 8～12 个关键音效，其余分批加入 |
| 网络音频反馈延迟 | 操作与声音不同步 | 高频关键音效本地化；低频音效预加载、缓存并允许静默降级 |
| 五步操作差异化过度 | 新手学习成本提高 | 入门模式放宽速度、停留、节奏和覆盖阈值 |
| 手势依赖机型不稳定能力 | 不同手机判定不一致 | 只使用位置、时间和速度等基础触控数据，不依赖真实压力值 |
| 为增强趣味加入过重动效 | 中低端手机卡顿、发热 | 限制并行动画；低性能降级；真机优先验收 |
| 音效过多或重叠 | 嘈杂、延迟、体验反而下降 | 统一音频管理、高频节流、分类音量 |
| “游戏化”破坏专业表达 | 非遗内容娱乐化或失真 | 趣味反馈服务于理解，不虚构工艺事实 |
| 外部素材链接失效 | 页面空白、汇报时无法展示 | 转存到项目可控云存储并保留本地占位 |
| 素材授权不清 | 无法公开发布 | 接入前登记来源与使用授权 |
| 演示数据污染正常统计 | 完成率和用户进度失真 | 演示状态隔离；协议未适配前关闭演示埋点和持久化 |
| 测试者招募延迟 | 第 4 周无法完成验收 | 阶段 1 开始时招募，拆为两轮并预留第 5 周缓冲 |
| 需求不断扩展 | 工期失控、核心体验迟迟不稳定 | 新需求按 P0/P1/P2 分类，非核心项进入下一版 |

## 11. 方案 A 的后续验证条件

方案 A 不删除，但必须满足以下条件后再考虑：

1. B+ 版本已完成真机验收；
2. 10 名新手中至少 8 名能独立完成五步；
3. 当前小程序没有阻断性缺陷；
4. 已经明确存在原生小程序无法实现、且对目标用户确有价值的表现需求；
5. 团队能够接受微信小游戏的独立工程、构建、测试和发布链路；
6. 有明确设备性能目标和可承担的长期维护成本。

满足条件后，只做一个 3～5 个工作日的独立技术验证，不直接重写全项目。

验证场景建议只选“打箔”：

- 搭建一个最小 Cocos Creator 微信小游戏工程；
- 实现一次敲击、节奏、粒子、危险状态和完成反馈；
- 在中低端 Android 与 iPhone 上测试帧率、启动时间和包体；
- 与当前原生小程序打箔环节进行用户对比；
- 验证结束后再决定停止、局部独立开发或进入完整方案 A。

方案 A 的工期应单独核算。以有经验的小团队估算，完整实现更接近 14～22 周；个人开发通常需预留约 4～8 个月，不应使用 10～16 周作为无风险承诺。

## 12. 项目决策规则

后续出现新想法时，按以下顺序判断：

1. 是否能提高新手完成率？
2. 是否能让错误原因更清楚？
3. 是否能提升五步差异、流畅度、真实性或展示质量？
4. 是否会增加离线包体积、设备负担或维护复杂度？
5. 是否需要改变微信小程序的技术路线？

前三项收益明确，且第四项成本可控，可进入 B+ 排期；若需要改变技术路线，则进入独立调研或方案 A 验证，不直接并入当前主线。
