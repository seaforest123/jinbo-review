## 1. 目标

从零建立一个可通过微信体验版二维码扫码访问的微信原生小程序，完成“首页 → 三步轻量工艺体验 → 数字结果页”的 P0 闭环，并验证 CloudBase 数据、核心埋点、真机运行和异常降级能力。

第一轮不以正式公开上线为目标。体验内容供项目团队、指导教师和受邀测试人员内部验证；未经专业确认的工艺、人物和历史信息不得作为事实发布。

## 2. 已确认的产品原则

- 第一阶段核心用户为广东高校学生，重点为18—24岁青年。
- 产品主线为“3分钟轻量工艺体验＋可选深度学习”，首页直接进入体验，不以课程、注册或知识测评作为前置。
- 制箔和贴箔保持并列候选，首次专业访谈后再锁定首版路线。
- 数字体验必须说明经过简化，不替代真实工艺学习。
- 3D／AR用于增强理解，不作为第一轮成败的唯一标准。
- 主流程不设置失败、扣分、倒计时、数值评分或公开排名。
- 目标值、测试结果和未来计划必须分别表述，不能把目标写成既有成果。
- 工艺真实性、内容审核、素材授权和研究知情同意属于否决性条件。

## 3. 第一轮范围

### 3.1 纳入范围

- 微信原生小程序工程及体验版发布配置。
- 首页、体验页、结果页、简化的金箔志入口和活动入口。
- 三个连续步骤的通用体验框架。
- 至少一个较高保真互动步骤，另外两个步骤允许采用点击、拖动或滑动。
- 路线、步骤、文案和素材的配置化读取。
- CloudBase 最小数据集合和核心行为埋点。
- 加载、弱网、视频失败和互动能力不足时的降级路径。
- 开发者工具测试、真机扫码测试和体验版二维码验收。

### 3.2 不纳入范围

- 正式公开上线和面向自然用户的公开传播。
- 制箔或贴箔路线的专业定稿。
- 完整三步高保真3D、完整空间AR或复杂动作识别。
- 登录、积分、排行榜、证书、收藏、商城、支付、直播和复杂会员系统。
- 复杂内容管理后台。
- 正式研究问卷、联系方式收集和研究样本配对。
- 未经审核的传承人身份、非遗级别、工艺历史和真实素材。

### 3.3 专业访谈时间线与双路线并行边界

制箔和贴箔两条候选路线在开发阶段并行占位，但并行准备本身有成本，需要设定边界：

- 两条候选路线在 `internal_placeholder` 状态下，只需满足“三步骤结构完整、可运行、界面标注候选示意”，不要求素材精修，避免团队在未定路线上投入过多美术和内容成本。
- 首次专业访谈应在开发环境自动化测试通过、开发者工具验收完成之前安排完成，作为体验版上传前置条件之一；具体日期由项目团队与指导教师协调确定，写入第10条发布流程的记录中。
- 若首次专业访谈无法在体验版上传前完成，第一轮内测允许以两条路线均为 `internal_placeholder` 状态提交体验版，但首页与体验页必须同时明确标注“候选示意，尚未经专业确认”，不得只标注其中一条。
- 访谈完成后按「12.1 审批流程」执行状态切换，不在 P0 阶段因为访谈延迟而扩大范围或新增第三条候选路线。

## 4. 技术架构

### 4.1 客户端

客户端采用微信原生小程序，不引入 uni-app、PHP、MySQL或自建服务器。页面层只负责展示和用户交互，工艺路线、步骤内容和媒体资源通过配置读取。

建议页面：

- `pages/home`：项目价值、三分钟承诺、内部测试标识、开始体验入口。
- `pages/experience`：开场片段、三个步骤、提示、重试、退出和降级。
- `pages/result`：数字作品、描述性反馈、文化提示和后续入口。
- `pages/archive`：内部测试期的简化金箔志内容列表。
- `pages/activity`：内部测试期的活动说明或友好空状态。

建议领域模块：

- `domain/route-config`：校验并提供候选路线和三步骤配置。
- `domain/experience-machine`：管理准备、进行、完成、退出和降级状态。
- `services/content-repository`：读取已允许用于当前环境的配置和内容。
- `services/event-tracker`：构造、缓存和提交行为事件。
- `services/capability`：判断3D、网络、视频和设备能力，选择交互适配器。
- `components/step-adapter`：为点击、拖动、滑动和 XR-Frame 交互提供统一完成接口。

### 4.2 CloudBase

第一轮只使用以下集合：

- `app_config`：版本、功能开关、当前候选路线、首页配置和测试环境标识。
- `content_items`：内部测试内容、状态、来源、审核信息和版本。
- `media_assets`：图片、视频、模型、授权引用和加载信息。
- `behavior_events`：匿名会话事件、设备能力、版本和测试账号标识。

不在第一轮创建 `research_contacts` 和 `research_responses`。若后续启动正式研究，联系方式、问卷和行为数据必须分开存储，并经知情同意后使用研究编号关联。

权限实现方式与职责边界：

- 客户端只拥有对 `behavior_events` 的写入权限（仅追加，不可修改、不可删除），以及对 `app_config`、`content_items`、`media_assets` 的只读权限，且只能读取审核状态和环境标识已允许在当前环境展示的记录。
- 审核状态（如内容从候选变为确认）、授权范围和路线配置的修改，一律通过云函数完成，云函数内部校验操作者身份和审批记录后才允许写入；客户端不得直接调用数据库写接口修改这三类集合。
- CloudBase 安全规则按集合分别配置：`behavior_events` 仅允许本人会话追加写入且不可读取他人数据；`app_config`／`content_items`／`media_assets` 对客户端一律只读，写权限仅开放给云函数所使用的服务身份。
- 埋点写入不做强身份校验（因为不收集身份信息），但通过匿名会话编号（见 7.1）做基本的频率限制，避免单一会话短时间内异常刷量；具体阈值可在开发环境测试阶段确定，不作为 P0 验收硬性指标。

### 4.3 路线配置

客户端不得根据页面代码判断“制箔”或“贴箔”。运行时读取一份路线配置，至少包含：

- 路线标识和显示名称；
- `candidate`、`confirmed` 或 `internal_placeholder` 状态；
- 三个有序步骤；
- 每一步的交互适配器、引导、反馈和降级方式；
- 关联的视频、图片、模型和内容 ID；
- 专业审核状态和允许使用的环境。

专业访谈前，配置状态保持 `internal_placeholder`，界面明确显示“候选示意／待专业确认”。访谈确认后替换配置和素材，不重写主流程。

### 4.4 较高保真交互的判定标准

为使“至少一个步骤完成较高保真交互验证”这一验收条款可被客观检查，约定以下判定口径（仅适用于 P0 阶段，不代表正式版标准）：

一个步骤可被记为“较高保真”，需同时满足：

- 使用拖动、滑动连续手势或 XR-Frame 三维交互中的一种，而非单一点击；
- 用户的操作幅度、方向或路径会实时影响界面反馈（例如力度、角度、覆盖范围），而非仅判断“点没点对”；
- 在开发者工具、一台 iOS 真机和一台 Android 真机上运行时无明显卡顿或掉帧，交互过程可连续完成而不需要中途重新加载；
- 若使用 XR-Frame，模型可正常加载、旋转或跟随手势变化，加载失败时按第6条降级规则切换为点击或拖动版本，并且降级后的版本不再计入“较高保真”。

验收时由测试人员在真机上实际操作一次并记录是否满足以上四点，作为第11条验收标准中该项是否通过的依据。

## 5. 用户体验

### 5.1 首页

- 首屏直接展示“开始3分钟体验”主按钮，无需登录或填写信息。
- 显示内部测试版标识。
- 提示数字体验经过简化，不替代真实工艺学习。
- 记录 `home_cta_click` 及入口来源。

### 5.2 体验流程

1. 用户进入体验，记录匿名会话并触发 `experience_start`。
2. 播放可跳过的3—5秒内部占位开场；静音状态可理解。
3. 第一步使用点击选择，验证工具／材料识别类交互框架。
4. 第二步使用拖动、滑动或 XR-Frame，作为较高保真技术验证步骤。
5. 第三步使用观察和轻量操作，验证检查／修整类交互框架。
6. 每步提供首次引导、按需提示、重试和即时描述性反馈。
7. 三步完成后触发 `experience_complete` 并进入结果页。

步骤名称和实际工艺含义均来自路线配置；上述三种交互仅定义技术角色，不构成对真实工艺步骤的专业判断。

### 5.3 结果页

- 展示可旋转或可观察的数字结果作品。
- 使用“细致、稳定、均匀”等描述性措辞，不显示数值评分或排名。
- 明确提示“你完成的是数字化轻量体验，不代表已经掌握真实工艺”。
- 提供再次体验、金箔志和活动入口。
- 分享能力仅在不要求姓名、手机号且用户主动触发时启用。

## 6. 异常与降级

- 加载过程中始终显示进度或明确状态，不出现无反馈空白页。
- 加载超过8秒时提示继续等待并允许退出。
- 加载超过15秒仍失败时，切换为2D、图文或视频替代路径。
- 视频失败时显示封面、字幕摘要和跳过入口，仍允许进入步骤。
- 弱网或断网时保留当前进度，网络恢复后允许重试，无需重启小程序。
- 交互适配器不可用时切换到点击、拖动或滑动版本。
- 埋点提交失败时保存在本地队列，后续重试；不得阻塞用户体验。
- 所有异常都允许返回或退出，不形成死循环。

## 7. 数据与埋点

核心事件包括：

- `home_cta_click`
- `experience_start`
- `video_play`
- `video_skip`
- `step_start`
- `step_hint`
- `step_retry`
- `step_complete`
- `experience_exit`
- `experience_complete`
- `result_action`

事件至少包含时间、版本、匿名会话编号、匿名用户编号、路线标识、设备能力、测试账号标识和事件参数。测试数据与未来正式数据必须可区分。

第一轮不收集手机号、微信号、姓名或其他直接身份信息。CloudBase 权限遵循最小权限原则，客户端不能直接修改审核状态、授权范围或管理配置。

### 7.1 匿名标识的生成与持久化规则

- 匿名用户编号在小程序首次启动时基于微信 `wx.login` 返回的 code 换取的 openid，经云函数单向哈希后生成，不存储或回传原始 openid，客户端本地缓存该哈希值，以便同一用户多次打开小程序时保持同一编号。
- 匿名会话编号在每次进入体验流程（即触发 `experience_start`）时重新生成，用于区分同一用户的不同体验批次；同一会话内的所有事件共用同一会话编号，退出体验或完成体验后会话结束。
- 用户重装小程序或清除缓存后，本地哈希值丢失，再次启动会视为新的匿名用户编号；这是已知且可接受的行为，P0 阶段不做跨设备或重装后的身份还原。
- 测试账号标识由测试人员在开发者工具或体验版中手动进入的入口参数决定，与匿名用户编号相互独立，用于在 CloudBase 中快速过滤团队自测数据，不影响匿名用户编号的生成逻辑。

## 8. 视觉与内容规则

- 视觉沿用项目文档的金色、棕色和暖白体系，强调材料质感但保持移动端清晰。
- 首屏突出单一主行动，不让文化长文压过体验入口。
- 交互反馈不只依赖颜色或声音。
- 占位素材和文案必须醒目标注“内部测试”“候选示意”或“待专业确认”。
- 未经审核的内容不得伪装为已发布内容。
- 不使用未确认的传承人姓名、身份、级别、机构或历史事实。

## 9. 测试策略

采用测试驱动开发，但按模块风险分级适用，避免展示型页面的严格 TDD 拖慢 P0 交付节奏：

- **严格 TDD（先写失败测试再实现）**：`domain/experience-machine`、`domain/route-config`、`services/capability` 中的降级判断逻辑、`services/event-tracker` 中的字段拼装与本地队列重试逻辑。这些模块状态复杂，一旦出错会影响主流程可用性或数据可信度，优先保证测试覆盖。
- **先实现后补测试（允许，但交付前必须补齐关键路径测试）**：`pages/home`、`pages/archive`、`pages/activity` 等纯展示型页面，以及视觉样式相关代码。这类模块变更频繁、逻辑简单，严格 TDD 的收益低于开发成本，但页面与领域模块的对接点（如“点击主按钮触发 `home_cta_click` 并跳转”）仍需在交付前补充测试。
- 两类模块的划分不是一次性的：若展示型页面后续新增复杂交互逻辑（例如结果页的旋转手势），该部分逻辑应下沉到独立模块并按严格 TDD 处理，而不是留在页面文件里免测试。

自动化测试重点覆盖：

- 路线配置的必填字段、三步骤顺序和状态校验。
- 体验状态机的开始、步骤完成、提示、重试、退出和最终完成。
- 8秒提示、15秒降级和交互能力降级判断。
- 事件字段、测试数据标记、本地队列和重试行为。
- 只允许当前环境显示相应内容状态。

人工验收包括：

- 微信开发者工具基础库兼容检查。
- 真实体验版二维码扫码进入。
- iOS和Android真机主流程测试。
- 弱网、断网、视频失败和降级路径测试。
- 未登录状态下完整完成三步体验。
- CloudBase 中事件可查询且不明显重复。

## 10. 发布流程

1. 在独立开发环境完成自动化测试和开发者工具验证。
2. 配置用户提供的小程序 AppID 和 CloudBase 环境 ID，不把密钥写入仓库。
3. 上传微信体验版，设置受邀体验成员。
4. 使用体验版二维码完成真机验收。
5. 记录版本号、上传时间、CloudBase 环境、已知问题和回退版本，以及首次专业访谈的实际完成情况（已完成／未完成，若未完成注明预计时间）。
6. 第一轮验收后保持体验版状态，不提交正式公开审核。

## 11. 第一轮验收标准

- 体验版二维码可由已授权测试成员扫码打开。
- 未登录用户可从首页连续完成三个步骤并进入结果页。
- 路线和步骤由配置读取，替换路线不需要修改页面主流程。
- 至少一个步骤按第4.4条标准完成较高保真交互验证，另外两个步骤具备可理解的轻量交互。
- 加载、视频、网络或设备能力异常时存在可完成的替代路径。
- 核心事件能够在 CloudBase 查询，测试数据可识别。
- 不出现未经专业确认的身份、级别、历史或工艺事实。
- 不公开使用未授权的图片、视频、录音、作品或模型。
- 版本、部署、测试、已知问题和回退方式有记录。

## 12. 后续闸门

首次专业访谈完成并取得可归档确认后，才能执行以下动作：

- 将路线状态从 `internal_placeholder` 改为 `confirmed`；
- 固化真实三步骤、术语、工具、材料和动作；
- 替换真实开场和步骤视频；
- 制作对外人物故事和文化内容；
- 将 PRD 升级到下一正式版本；
- 评估是否进入公开测试或正式研究。

### 12.1 candidate → confirmed 的审批流程

为避免“否决性条件”在执行层面落空，路线状态从 `internal_placeholder`／`candidate` 变为 `confirmed` 须经以下流程，并留痕存档：

1. 首次专业访谈完成后，项目团队整理访谈记录（受访人、机构或身份信息、访谈时间、确认的工艺步骤要点），形成书面纪要。
2. 指导教师对纪要中的工艺真实性、术语准确性进行确认签字（或书面等效确认，如邮件回复），作为专业确认的凭证。
3. 若访谈内容涉及素材授权（照片、视频、模型等），需附带授权范围说明，明确是否可用于本轮内测、是否可公开传播。
4. 以上材料存档后，由项目团队负责人在 `content_items` 对应记录中登记审核信息（审核人、审核时间、依据的纪要编号），并通过云函数将该路线状态由 `internal_placeholder` 改为 `confirmed`；客户端不参与也不能触发此状态变更。
5. 状态变更后，`internal_placeholder` 时期使用的占位素材和“候选示意”标注同步下线或替换，不与已确认内容混用。
6. 若同一次访谈只确认了两条候选路线中的一条，另一条路线保持 `internal_placeholder` 状态，不因为一条路线确认而连带变更另一条。
